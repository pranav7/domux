# M3: agents

## What M3 is

One record per AI coding session, fed by two independent sources: the agent's own hooks and a
process observer on the core's tick. A pure state machine over (state, event). Recaps and
session names read from the agent's transcript. The Agents box in two places, the sidebar and
the agents overlay under `leader a`, drawing one row grammar. The count at the left of the top
bar. Claude resume, by keyboard, by CLI and by API. Hook installers for Claude, Codex and
OpenCode. The `SessionStart` context block that tells an agent where it is and what it can ask
domux.

Architecture spec section 11, the amended M3 row, verbatim: "Records, `agent report` reading
the pane environment M1 injects, observer, state machine, recaps, session names, hook
installers for Claude, Codex, and OpenCode, Claude resume, `SessionStart` context. Interface
spec section 6: the agents overlay under `leader a` and the Agents box beneath the sidebar's
Projects box, the session-name-first agent row (three lines in the overlay, two in the
sidebar), dot colours, unseen, the working glyph and word, sort order, `Enter` to open or
resume, and the count in the top bar."

Also in M3, because the roadmap puts them there: `schema_version = 3` with the migration from
2, `[resume]` in the config, `"a" = "agents.open"` in the default keymap, `Tab`, `C-j` and
`C-k` between the sidebar's boxes, `C-h` entering the sidebar by row overlap, the `agent` and
`agents` namespaces and `workspace.resume`, the six `agent.*` events, the CLI forms, and the
cut-over.

What M3 does not cover: notifications, toasts, desktop notifications, sound, mute, messaging
delivery (`agent.send`, `agent.read` and `agent.wait` are declared and answer `unavailable`),
usage, stay alive, `doctor`, all M4; the in-box action keys of Artboard 4, deferred; Codex and
OpenCode resume, V2.x; screen-content agent detection, V2.x.

### A note on the binary name in this document

Commands are named without the binary: "the report subcommand", not the whole line. M1's
`crates/domux-core/src/names.rs` carries a workspace test that fails if the name appears
anywhere else in `crates/*/src`, because the cut-over renames it and the guard is what makes
that a one-line change. This document is written the same way for the same reason: it was
written days before the rename. `AGENTS.md` and `docs/milestones/m1.md` predate the rule and
still spell the old name in prose, and the cut-over task does not list either among the files
it changes, so they go stale unless somebody remembers them.

## The record

`domux_core::model::agent::Agent`. The architecture spec's 3.2 fields, plus `name`, plus the
four decision record 0012 adds: `workspace`, `last_pane`, `transcript_path`, `source`.

Six states: `working`, `waiting`, `compacting`, `idle`, `exited`, `unknown`. `unknown` means an
agent is running and nothing has reported on it. It is never `idle`, because `idle` is a thing
an agent said and `unknown` is the absence of anything said (principle 4). A recap that did not
arrive is absent. A session name is absent until the agent sets one.

Eleven events: the nine hook events Claude Code names, plus the observer's two, `Observed` and
`ProcessGone`. `transition(state, event)` is a pure function and is table-tested over all 66
pairs in `crates/domux-core/src/model/agent.rs`. **Never add a state or an event without
extending the table**: a state is a row, an event is a column in every row. The table is a
`const` array, and its test asserts that `AgentState::ALL` is still 6 long, that
`AgentEvent::ALL` is still 11, and that it checked 66 pairs, so a new state or event turns that
test red rather than slipping through untested.

`attention(from, to)` says when a transition turns `unseen` on: an agent starts waiting, goes
from working to idle, or exits. M4's notifier keys its `[notifications] on` list off the same
function, so M4's toast and the dot answer the same question rather than two that drifted
apart.

## Two sources write records

**Hooks.** The agent runs the report subcommand, which reads its pane from `DOMUX_PANE`, reads
the payload from standard input, and calls `agent.report`. Three adapters in `agents::hooks`
turn a Claude, Codex or OpenCode payload into one `AgentEvent` and the fields around it. A
report from outside a domux pane exits 0 in silence, and so does a report to a server that is
not running: the same hook lines run under V1's panes until the cut-over, and a hook that fails
is an interruption in the agent's session.

**The observer.** `agents::observer::run`, on the core's once-a-second tick, over M1's
`ProcessInspector`. Decision record 0009 records why it is a function in the tick rather than a
task.

What the two sources buy is narrower than "either corrects the other". The observer does three
things and only three: it creates an `unknown` record for an agent nobody has reported on, it
binds a process id to a record a hook made, and it exits a record whose own process id is gone.
It never sets a state. `transition` says so outright: `(s, Observed) => s` for every live state.

So a record exists whether or not the hooks are installed, and an exit is seen either way. **A
lost hook is not made good later.** A `Stop` that never arrives leaves the row `working`, with a
turning glyph, a working word and a place above every idle row, for as long as the process lives.
A row stuck on `working` is the shape hook loss takes here, and it is worth going to look at
rather than waiting out.

Order matters between hooks. An observer tick before or after a hook reaches the same record
either way, because the observer finds a record by its pane, and a hook finds one by session id
first and by the pane second. Two hooks against each other are the state machine, where order is
the whole thing.

### The observer's one rule

A record exits when its **own** process id goes away, or when its pane goes away. Never because
the foreground changed. An agent running a tool puts that tool in the foreground, and the tool
can itself be an agent: a session that runs another kind, or its own kind, has to survive that.
Reading the name in front of the pane would exit a live record, and by decision record 0010 a
hook after an exit changes nothing, so the record would stay exited for the rest of that
session.

| In the foreground | The record on the pane | What happens |
|---|---|---|
| kind K, pid P | kind K, holds P | nothing |
| kind K, pid P | any kind, holds a live pid | nothing: what is in front is a tool it is running |
| kind K, pid P | any kind, holds a dead pid other than P | the record exits, and P starts a record of its own |
| kind K, pid P | kind K, holds no pid | bind P: a hook made the record and this is its process |
| kind K, pid P | kind J, holds no pid | nothing, in either direction |
| kind K, pid P | none | a new `unknown` record for P |
| not an agent | holds a dead pid | the record exits |
| not an agent | holds a live pid, or none | nothing |

A dead own process exits the record and the process in front gets a new one rather than the
record being rebound onto it. Rebinding would merge two sessions: the dead session's session id
would be overwritten by the new session's first hook, and the session that ended would stop
being resumable.

## The agent API

M1's socket, M1's framing, M1's newline-delimited JSON control API. M3 adds two namespaces and
one method to each of two more. `agent` (singular) is the records namespace; `agents` (plural) opens and
closes the overlay.

| Namespace | Methods |
|---|---|
| `agent` | `agent.list`, `agent.get`, `agent.self`, `agent.report`, `agent.focus`, `agent.dismiss`, `agent.resume`, `agent.send`, `agent.read`, `agent.wait` |
| `agents` | `agents.open`, `agents.close` |
| `focus` | `focus.next_region` (new in M3) |
| `workspace` | `workspace.resume` (new in M3) |

`agent.send`, `agent.read` and `agent.wait` are declared with their final params and answer
`ApiError::unavailable` naming M4. They are on a register, `STILL_UNBUILT` in `core.rs`, which
fails two ways: implementing one without deleting its line fails, and adding an `unavailable`
arm without a line fails. M4 fills the handlers and does not change the params, so the CLI shape
and the schema do not move.

Six events: `agent.created`, `agent.state_changed`, `agent.recap_changed`, `agent.exited`,
`agent.dismissed`, `agent.unseen_changed`. `agent.created` carries the record's `source`, so a
subscriber can tell a session that reported itself from a placeholder the observer made.

`agent.list` answers in the interface's own sort order, so the CLI and the box agree: waiting,
then working and compacting, then unseen idle, then quiet idle, then unknown, then exited.
Within each band the newest activity comes first, and the agent id breaks a tie so two records
that changed in the same second keep one order between renders. It also answers `red_dots`, the
number the top bar's count shows.

One implementation per operation. `Enter` on an exited row in the Agents box, the resume
subcommand and `agent.resume` are one function. `Enter` on a live row, the focus subcommand and
`agent.focus` are one function.

### The addressing rule

`Model::resolve_agent_target` takes an agent id, a workspace with one agent, or
`workspace/tab`, and answers the record or a refusal that lists the candidates. M4's messaging
verbs use it unchanged.

## The hook contract

The installers write one command line per event: the binary's absolute path, then
`agent report --agent <kind>`. The path is `~/bin/<binary>` when that symlink exists and the
running executable otherwise, because a hook runs in the agent's environment and domux does not
control its PATH. A path a shell reads as one word is written bare; anything else is single
quoted.

| Kind | File | Events |
|---|---|---|
| claude | `~/.claude/settings.json` | `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Notification`, `PreCompact`, `PostCompact`, `Stop` |
| codex | `~/.codex/hooks.json` | `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Stop` |
| opencode | `~/.config/opencode/plugins/domux.js` | none written here; the generated plugin listens for its own |

**Installers preview by default.** The install subcommand without `--apply` writes nothing and
prints what would change. `--apply` backs the file up as
`<path>.domux-backup-<YYYYmmddHHMMSS>`, writes `path.tmp` and renames, and is idempotent: a
second run changes nothing. It replaces its own older lines and V1's `ai-state` lines, and
leaves lines the author wrote alone. **Never run `--apply` against `~/.claude` or `~/.codex`
without the author saying so**; the cut-over task is the one place it happens.

The `SessionStart` reply carries the context block, which the report subcommand writes to
standard output and Claude Code adds to the session's context. It names the agent's id, kind,
place and working directory, says how many other agents are running, names the two verbs that
work in M3, and says the three messaging verbs fail until M4. It describes that refusal rather
than quoting it: each verb refuses in words of its own, naming its own method.

## Resume

Resume types V1's line into the pane the record last ran in, with one carriage return after it,
so the pane's shell reads it as one line and runs it and the line is in that shell's history
afterwards. What domux does not do is start the process itself: the agent comes back as a child
of the shell the author was already using, not as something the server spawned.

```
cd '<cwd>' && command -v claude >/dev/null 2>&1 && claude --resume '<session id>'
```

Only the last part is the manifest's; `AgentManifest.resume_command` holds
`claude --resume {session_id}` and nothing else. Both guards come from `resume::resume_line`, and
the `cd` is the load-bearing one: `claude --resume` is scoped to the project directory and finds
no session from anywhere else. `command -v` is second, so a machine without the CLI installed
leaves an untouched prompt in the pane instead of an error nobody asked for. A record with no
directory gets the line without the `cd`, because `cd ''` fails where leaving it off works.

The session id and the directory are shell quoted; the process name is not, because it comes from
a manifest this repository declares rather than from an agent or the file system.

Only Claude resumes in V2.0. Codex and OpenCode declare no resume command and their refusal
names the kind and says to start it by hand. A record with no session id refuses by naming the
install subcommand, because a session id is what a hook gives.

A resume does not change the record's state. The record stays `exited` until the new session's
first `SessionStart` arrives, which is decision record 0010's other half: typing a line into a
pane is not evidence that a session started.

`[resume] agents = "manual"` is the default. `"auto"` resumes every resumable record when the
**server** starts, not on every attach.

### The gates


### CI runners

`.github/workflows/ci.yml` runs the four gates on macOS arm64 (`macos-latest`), Linux x86_64
(`ubuntu-latest`) and Linux aarch64 (`ubuntu-24.04-arm`), plus a cross build for
`x86_64-apple-darwin`. M3 adds an "Agent tests" step to the matrix job, ahead of the workspace
run so a failure there names itself instead of arriving inside a run of the whole suite. macOS
and Linux both matter for agents in particular: the process inspector reads the foreground
process and a process's working directory through libproc on macOS and `/proc` on Linux, and
the observer is that trait's largest user.

## Deviations from the plan

### A clear takes only the exited records

The plan's assumption 32 says clearing or deleting a workspace removes its records, from the
architecture spec's "until you dismiss it or clear the workspace". That wording is about exited
records and does not settle the live case, and a clear keeps the workspace and its panes: an
agent still running in a cleared slot is still running. So a clear now dismisses only the
records whose session is over, and a live record keeps its id, its session id, its recap and its
name. A delete is unchanged and takes everything, because the workspace itself is gone.

Both paths give back a record's caches through one place, `Core::forget_agent_caches`. Its two
halves are not equally live on both: a clear only ever reaches exited records, and an exited
record holds no working word, so the word half does nothing there while the transcript half
does. On the delete route, which takes working records too, both halves matter.

### `AgentKind` has no `clap::ValueEnum` derive

Contract item 31 asks for one. `domux-core` is the pure model and does not depend on clap, and
this plan adds no crate, so the CLI parses the kind through `FromStr` behind a `value_parser`.
The reader sees the same three kinds and the same refusal either way:
`unknown agent kind "gemini"; expected claude, codex or opencode`.

### `Core.pending_writes` does not exist

Contract item 15 puts it beside M1's `pending_spawns` and `pending_kills`. `pane.send_text`
already writes into a pane in place, so a second mechanism for the same operation would be a
second implementation. `Ctx::write_to_pane` points at the existing one instead. **M4 will go
looking for the contract name**; this paragraph is where it is answered.

### `CoreMsg::PaneFd` does not exist

Contract item 29 declares it behind `Harness::set_foreground_for`. `FakeSpawner` already records
every spawn request in order, so it hands out a descriptor per pane and the harness asks the
spawner. One place computes the number and no round trip through the core is needed.

### `agents::context::place_without_tab`

Added beyond contract item 23. The sidebar's agent row has no room for the tab (interface spec
6.3), and one function answering both forms is what stops the overlay's place line and the
sidebar's from drifting apart.

## Still open

Nothing below is a defect being hidden. Each was decided deliberately and carries its reason,
because an item without its reason reads as an oversight.

### Before or during the cut-over

- **A broken `~/bin/<binary>` symlink changes what goes into the hook file.** The installer
  prefers the symlink when it `exists()`, and a broken symlink reads as absent, so it falls back
  to the running executable. That is reachable: the symlink points into `target/release`, so a
  `cargo clean` breaks it, and `--apply` in that state writes a `target/` path into the real
  settings file. The fallback is the right behaviour; check the symlink before the cut-over.
- **The hook fixtures are specified, not recorded.** The payload shapes come from the plan
  rather than from real Claude, Codex or OpenCode sessions, because capturing them needed writes
  under `~/.claude`, which this milestone forbids. If a real payload names a field differently,
  the adapter reads that field as absent and the gap shows at the cut-over. Recording real
  payloads once closes it.
- **`PostCompact` may not be an event Claude Code emits.** It is in the installed Claude event
  set. The state machine does not strand if it never arrives, because a record leaves
  `compacting` on the next ordinary event, so the cost is one line in the settings file that
  never fires.
- **The `/rename` shape is unverified against real usage.** The session name is read as the last
  `<command-name>/rename</command-name>` entry's `<command-args>`. A search of all 152 of the
  author's transcripts found no real `/rename` invocation, so the parser and its fixture both
  encode the plan's shape rather than an observed one.

### What M4 should know

- **`Core.pending_writes` is in the shared contract and deliberately does not exist.** See the
  deviation above.
- **`auto` resume at start now runs through the `workspace.resume` handler.** A change to that
  handler's filtering silently changes what happens at server start. The tests catch a changed
  outcome, not a changed intent.
- **`AgentKind` has no `clap::ValueEnum` derive**, against contract item 31. See above.
- **One session resumes per pane, with no override.** A reader who wants an older record resumes
  it by name once the pane is free, and the skipped line says so.
- **`observer::run` can panic on a pane the model does not hold.** Decision record 0009's last
  section has the detail. M4 adds callers, and one `continue` buys the invariant back.

### Facts about the test suite

- **`two_working_agents_never_share_a_word` is weaker than its name.** It passes on a build where
  the uniqueness walk is deleted entirely, because two differently numbered records hash apart
  anyway and an interface test cannot choose ids to force a collision. The rule is genuinely held
  by `labels::tests::no_two_agents_on_screen_share_a_word`, which takes forty ids. A later task
  citing the interface test would cite the wrong test.
- **The agent tests read state across a window, not a barrier.** `Core::run` sends the API reply
  before it publishes the snapshot, so `Harness::model()` straight after an awaited call is a
  race. Measured at 80 consecutive runs on 8 threads with no failure. **Only `agent_observer.rs`
  guards against it**, through its `agents()` helper, which makes a `server.info` round trip
  before every read and so is a real barrier: the core takes its messages in order, so an
  answered method proves every message sent before it was handled. `agent_report.rs`'s
  `only_agent` reads the snapshot straight after an awaited report, at thirteen call sites, and
  `agent_api.rs` and `agent_resume.rs` read it without a round trip too, mostly for client and
  workspace lookups rather than for records. It cannot be fixed per test: awaiting a frame first
  would hang the tests that assert nothing changed. The fix is a barrier in `testing.rs`.
- **The install preview's gutter is 18 columns**, derived from today's longest event name, and
  nothing enforces it. An event of 18 characters or more breaks the column silently, because all
  four pinned strings use short names.
- **A three-line loop in `resume_agents_on_start` is covered only by the refusal it delegates
  to.** Closing it needs the `FakeSpawner` handle threaded out of `core_with`, which changes that
  helper's return type across nine call sites in other tests.
- **`install codex` and `install opencode` are never run through the CLI.** Every CLI install
  test uses `claude`; all three kinds are covered at the library level.
- **`tests/git.rs` flaked once** in a full-suite run and passed on the re-run and on a second full
  run. It shells out to git and spawns two concurrent `git worktree add` threads, which lost
  git's index lock once under load. Possibly pre-existing; it touches nothing M3 changed.

### One pattern worth sweeping

**Four `RegionKind` name-list defects were found in this milestone**: `focus_after_pop`,
`focus_returning_from_overlay`, `sidebar.hide` and `clear_notes_read_by`. Each listed the regions
it knew about and fell through silently when M3 added two more. Two sites that are correct today
are correct only because they are exhaustive matches that would fail to compile. The durable fix
is to prefer an exhaustive match, or a predicate like `RegionKind::is_box()`, over a list of
names wherever the question is really about a category. Somebody should sweep the remaining lists
once rather than find the fifth.
