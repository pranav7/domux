# M1: a multiplexer

## What M1 is

Server, socket, attach protocol, headless test client, single core task, PTY lifecycle, tabs,
splits, zoom, copy mode with Enter-to-copy, focus model with the author's `C-h/j/k/l` bindings
and passthrough, keymap engine with leader and `domux.toml`, structure persistence and restore.
Interface spec section 4: the top bar with `project › workspace`, the tab row with the filled
current tab, pane boxes with the foreground command in the border, the accent on the focused
pane, the `zoomed` flag, `leader ,` naming the current tab in its own cell. One implicit
plain-folder project.

What M1 does not cover: no projects beyond the one implicit plain-folder project, no agents,
no notifier.

## Exit criterion

"The author lives in it as a tmux replacement for one directory for a full day, including
detach and reattach."

## The client-server protocol

One unix socket at `paths::socket_path()` carries two protocols and the first byte picks them:
`{` starts a newline-delimited JSON control API request, anything else starts a length-prefixed
attach frame. `proto::is_control_api_first_byte` is the one place that decides, and
`socket::handle` is its one caller: it reads a single byte, routes the connection, and hands
that byte on to whichever reader takes it.

The two can never collide. An attach frame opens with the top byte of a body length that
`MAX_FRAME` caps at 64 MiB, so that byte is at most `0x04`; `{` is `0x7b`. A const assertion
beside `MAX_FRAME` holds the relation, so raising the cap to `0x7b000000` or above breaks the
build instead of misrouting a connection.

### Framing

Four-byte big-endian length, then bincode. `proto::encode` writes the prefix and the body;
`proto::Decoder` accumulates bytes and yields whole messages, returning `Ok(None)` while the
buffer holds less than one.

`MAX_FRAME` is 64 MiB. A length above it is `ProtoError::FrameTooLarge`, which is terminal for
the stream: the caller drops the connection. The offending bytes stay at the front of the
decoder's buffer on purpose, so a caller that ignores the error gets the same error forever
rather than silent progress - resynchronising past a bad frame would mean trusting the length
the failed decode just called into question. `encode` refuses to write an oversized frame for
the same reason, rather than emitting a prefix the peer will reject.

### Handshake

`PROTOCOL_VERSION` is 1. It is bumped when a message shape changes.

The client's first framed message must be `Hello { version, protocol, cols, rows, caps }`;
anything else ends the connection. `version` is the client binary's `CARGO_PKG_VERSION`.

The server accepts only when `version` equals its own and `protocol` equals
`PROTOCOL_VERSION`. A match answers `Welcome { client, version }`, carrying the `ClientId` the
model just seated, and the next frame is a full one. A mismatch answers
`Refused { reason }` and closes; the reason names both versions and the way out, so a stale
server after an upgrade fails with an instruction instead of corrupt output.

`Capabilities` carries what the client's outer terminal can do: `truecolor`,
`kitty_keyboard`, `hyperlinks`, `osc52` (the outer terminal accepts OSC 52 for the clipboard),
and `default_fg` / `default_bg`, the terminal's own default colours when it answered OSC 10
and 11. Each is absent rather than guessed when the terminal did not say.

### Client to server

`ClientMsg`:

- `Hello` - the handshake above. After the handshake the server ignores it.
- `Key` - one `KeyEvent`, routed by `input::route_key`: the leader chord, then a global
  binding, then the pane. Every key produces a frame.
- `Paste` - text the outer terminal bracketed; the emulator encodes it and the focused pane's
  PTY takes it.
- `Resize` - the client's new screen size. The model records it, the client's diff buffer is
  cleared, and the next frame is full.
- `Focus` - the outer terminal gained or lost focus; the focused pane's emulator encodes it
  for the child.
- `Detach` - end this view. The server replies `Detached` and forgets the client; the panes
  and the structure stay.
- `ClipboardFailed` - the client could not write the clipboard. The reason becomes an action
  hint in the clock's place.

### Server to client

`ServerMsg`:

- `Welcome { client, version }` - the handshake succeeded; `client` is this view's id.
- `Refused { reason }` - the handshake failed; the connection closes after it.
- `Frame(FrameDiff)` - the cells that changed, below.
- `Clipboard(String)` - text for the outer terminal's clipboard, from copy mode's Enter.
- `Bell` - a pane rang.
- `Detached { reason }` - this view is over and the stream ends. The reason is
  `proto::SERVER_STOPPED` when the whole server is going away rather than one view; that
  constant lives beside the message so the server writing it and the client reading it are
  one string rather than two literals a reword could part.

### Frames

The server renders one ratatui `Buffer` per client, diffs it against that client's previous
buffer, and sends only the cells that changed.

`FrameDiff { full, cols, rows, cells, cursor }`. `cells` is a `Vec<CellUpdate>`, each carrying
`x`, `y`, `symbol`, `fg`, `bg`, an optional `underline` and ratatui's `modifiers` bits. Colours
travel as `WireColor`: `Reset`, `Indexed(u8)` or `Rgb(u8, u8, u8)`. `cursor` is an optional
`CursorState { x, y, shape, blink }`; `None` hides the cursor.

`full` means the client must clear first and the frame carries every cell. It is set on
attach, after a resize, and after a send that could not be queued - a full channel means the
client never received the state the server diffed against, so the next frame replaces the
whole screen rather than diffing against a frame that was never seen. When nothing changed and
the frame is not full, no message is sent at all.

### The control API

Newline-delimited JSON on the same socket: one `Request { id, method, params }` per line, one
`Response { id, result | error }` per line. `params` defaults to an empty object. Errors carry
a stable `ErrorCode`. `events.subscribe` is the exception to one-response-per-request: it
answers once, then streams one JSON event per line until the connection closes.

The M1 namespaces are `server`, `client`, `config`, `tab`, `pane`, `focus` and `events`, plus
the bare `help`:

| Namespace | Methods |
|---|---|
| `server` | `server.info`, `server.stop` |
| `client` | `client.detach` |
| `config` | `config.reload` |
| `tab` | `tab.list`, `tab.create`, `tab.rename`, `tab.clear_name`, `tab.close`, `tab.select` |
| `pane` | `pane.list`, `pane.split`, `pane.close`, `pane.focus`, `pane.zoom`, `pane.copy_mode`, `pane.resize`, `pane.send_text`, `pane.send_key`, `pane.read` |
| `focus` | `focus.left`, `focus.right`, `focus.up`, `focus.down`, `focus.last`, `focus.region`, `focus.pane` |
| `events` | `events.subscribe` |
| (bare) | `help` |

The generated reference is `domux2 api schema`, which prints every method's params and result
schema plus the event, request and response schemas. It needs no server. One implementation
per operation: a keybinding, a CLI subcommand and an API request all reach the same handler in
`domux_server::api`.

## Deviations from the plan

### Usage errors exit 2, not 1

The plan's Interfaces line for the CLI says "exit status 0 on success, 1 on any error". A
usage error - a missing or unknown subcommand, `domux2 pane`, `domux2 nonsense` - exits 2
instead. Two is clap's default and the Unix convention for "you typed it wrong", and a script
that tells a mistyped command from a command that ran and failed reads exactly that
difference. The plan's `1` was written without the convention in mind, and narrowing working
conventional behaviour to match a plan line would make the tool worse.

Every real failure still exits 1: a rejected config, a missing tab, a server that is not
running, a call the server did not answer.

### Bare `domux2` inside a pane refuses to attach

Bare `domux2` in a shell that is already inside a pane refuses instead of attaching. A second
whole screen drawn inside one pane of the screen it is drawing takes the keys from the outer
client (principle 1) and puts a second accent border on the screen (principle 2), and nobody
types it there wanting that. The detection is `DOMUX_PANE`, which the server exports into
every pane. `domux2 attach` typed in full still attaches, and every other subcommand is
unaffected: reaching the server from a shell in a pane is why `DOMUX_SOCKET` is exported.

### The pane shell is a login shell

The plan says a pane with no command runs the configured shell; it does not say how. It runs as
a *login* shell, argv[0] prefixed with `-`, which is what every terminal emulator does when it
opens a window. A shell config keeps its PATH, its aliases and its functions in the login files
- zsh reads `.zprofile` only for a login shell - so the other reading would hand the user a
shell missing everything they had configured. Found by daily driving: `z`, `c` and `srczsh` were
all gone in a pane and present in a terminal.

The shell reaches the spawner as `SHELL` in the pane's environment rather than as the command,
because a login shell is the one form `CommandBuilder` will not take a path for. So a pane also
reports the shell it is actually running when a program asks `$SHELL`, which it did not before.
A shell that cannot be run is refused by name: the login form would otherwise fall back to the
password database and run a different one, turning a typo in `terminal.shell` into a setting
that silently does nothing.

### Panes are named by argv[0], not by the executable path

The plan says a pane's box carries the foreground command's name. On macOS that was read from
the executable path, which is the wrong fact for a versioned install: `~/.local/bin/claude`
resolves to `.../claude/versions/2.1.263`, so the box read `2.1.263`. It now reads argv[0] and
falls back to the path, which is what Linux already did through `/proc/<pid>/cmdline`.

### No gap between neighbouring boxes

Interface spec assumption 18 puts one cell between neighbouring boxes. That left three rows of
chrome between two stacked panes - a bottom border, a blank row, a top border - and every box
already draws its own edge, so the blank row separated nothing that was not separated. `GAP` is
0 and the borders touch.

### A side-by-side split is on `\`, not `|`

The spec's keymap puts `pane.split right` on `|`. It is on `\`: the same physical key without
the shift, for something done many times an hour. One key, not both, because two bindings for
one action leave `key_for` picking which of them the help overlay prints.

### A reload that loaded says so

The plan gives `config.reload` a result but no notice. A reload changes nothing on screen, so
without a word for it the key looks dead (principle 8); it now puts "config reloaded" in the
clock's place until the next key. A reload that *failed* adds nothing there, because the config
error already stands in the top bar naming the file, the line and the way to fix it.

### `<leader> x` closes a tab, and asks first

The plan gives `tab.close` no binding, so there was no way to close a tab from the keyboard.
It is on `x`, and the key asks before it acts because closing takes every process in the tab
with it (principle 10). The API method does not ask - see the commit for why.

### `server status` reports the leader

The plan's report lists the socket, the state directory and the config file. It lists the
leader too. The config file is read at start and on `config.reload`, so a file edited since
can disagree with the server, and when it does there was no way to find the key that works:
the help overlay names it, and opening the help overlay needs it.

### A binding to an action the server cannot do is a warning

The plan warns on a bad key name. A bad *action* was accepted in silence, so a typo produced
a `config reloaded` with no complaint and a key discovered to be dead only by pressing it.
Actions are now checked against the methods and their arguments at load. The binding is kept
rather than skipped, unlike a bad key: it can be represented, and keeping it means the key
answers with the reason instead of falling through to the pane.
